RecPack: An(other) Experimentation Toolkit for Top-N Recommendation using Implicit Feedback Data

Lien Michiels, Robin Verachtert (Froomle · University of Antwerp, 공동 제1저자) · Bart Goethals (University of Antwerp · Monash University · Froomle) · RecSys 2022 Demos · Best Demo

원문 확보: arXiv와 Semantic Scholar에는 공개 PDF가 없어, 저자 홈페이지에 링크된 University of Antwerp 기관 저장소의 동료심사 저자 원고(4쪽, ACM 출판본 pp. 648–651에 해당)를 전부 읽고 작성했다. 데모 논문이라 실험 수치는 없다. 본문의 일부 배경 설명(수식, 공식 문서의 시나리오 이름)은 논문 밖의 일반 지식이며, 그 경우 따로 표시했다.

3분 요약

한 문장 핵심. RecPack은 implicit feedback 기반 Top-N 추천 실험을 위한 Python 툴킷이다. scikit-learn과 같은 fit/predict 인터페이스로 데이터셋 → 전처리 → 분할(시나리오) → 알고리즘 → 후처리 → 지표 → 파이프라인 전 과정을 모듈로 제공한다. 목표는 "벤치마크 돌리기"가 아니라 연구자가 자기 알고리즘을 노트북에서 반복 개발하며 올바르고 재사용 가능한 실험을 하도록 돕는 것이다.

풀려는 문제. 추천 연구에서 코드 공개는 늘었지만 품질이 낮거나 환경 설정 안내가 없는 경우가 많다. 저자들이 인용한 Trisovic 등의 조사에 따르면 공유된 연구 코드로 실험이 재현되는 경우는 약 25%에 그친다. 재현되더라도 새 데이터나 새 맥락에 다시 쓸 수 있는지(재사용성)는 별개 문제이고, 재사용 가능한 코드를 쓰는 데는 큰 노력이 든다.

핵심 아이디어. 실험 파이프라인의 각 단계를 표준 객체로 만들고, 기본값을 합리적으로 정해 둔다. 데이터셋마다 기본 전처리 필터가 있어 다른 연구와 비교가 쉬워지고, 내장 알고리즘의 하이퍼파라미터는 원 논문의 최적 설정으로 초기화된다. 공통 로직을 담은 세 개의 추상 기반 클래스(아이템 유사도, 행렬 분해, PyTorch 모델)를 상속하면 자기 알고리즘의 고유한 부분만 구현하면 된다. 검증 세트를 따로 떼어 하이퍼파라미터를 튜닝하므로 데이터 누수도 줄어든다.

주요 결과. 정량 실험 결과는 없는 데모 논문이다. 기능 면에서는 20개 이상의 알고리즘(아이템 유사도, 분해, 오토인코더, 세션 기반, 시간 인지), 7종의 전처리 필터, 문헌에 등장하는 거의 모든 train/validation/test 분할을 담은 시나리오 모음, 사용자별 세부 결과를 볼 수 있는 지표를 제공한다. 유지보수 측면에서는 모든 기여를 리뷰·테스트하고 테스트 커버리지 90% 이상을 유지하는 것을 목표로 한다. 데모에서는 MovieLens25M에 WeakGeneralization 분할을 적용해, 직접 구현한 MLP(NCF 계열)를 WMF·BPRMF와 비교한다.

한계와 남는 질문. 논문 시점에는 beyond-accuracy 지표(다양성·커버리지 등)와 하이브리드·콘텐츠 기반 알고리즘이 없어 향후 과제로 남았다. implicit feedback의 Top-N만 다루므로 평점 예측이나 피처가 풍부한 CTR 랭킹 모델과는 범위가 다르다. 라이선스가 AGPL이라 사내 서비스 코드에 그대로 섞어 쓰기에는 법무 검토가 필요하다. 다른 툴킷과의 정량 비교(속도, 같은 설정에서 같은 수치가 나오는지)는 논문에 없다.

섹션별 상세 해설

1. 서론 — "또 하나의" 툴킷이 필요한 이유

제목의 "An(other)"는 자조적인 농담이다. 이미 추천 툴킷은 많다. 저자들이 예로 드는 Elliot, DaisyRec(Sun 등), RecBole이 대표적이다. 그런데 이들은 주로 벤치마킹, 즉 최신 알고리즘들을 빠르고 정확하게 비교하는 데 초점을 맞춘다. 그래서 설정 파일이나 명령줄 인터페이스로 실험을 정의하게 되어 있다.

RecPack의 위치는 다르다. 새 알고리즘을 만드는 연구자는 노트북에서 코드를 고치고, 돌려 보고, 버그를 잡는 과정을 수없이 반복한다. 이 반복 개발을 돕는 라이브러리가 목표다. 그래서 설정 언어 대신 Python 객체를 직접 조합하는 방식을 택했고, 인터페이스는 scikit-learn을 본떴다. scikit-learn에 익숙한 데이터 과학자라면 별도 학습 없이 쓸 수 있다는 것이 저자들의 주장이다.

저자들은 이 도구로 연구자가 할 수 있는 일을 세 가지로 정리한다. (1) 추상 기반 클래스를 이용한 빠른 알고리즘 개발, (2) 여러 시나리오·지표에서 최신 기준선과 비교, (3) 기준선과 자기 모델 모두를 데이터 누수를 최소화하며 하이퍼파라미터 튜닝. 또한 "프로덕션 마인드셋"을 강조한다. Froomle이라는 추천 솔루션 회사에서 만든 도구답게 기여는 엄격히 리뷰·테스트하고, 테스트 커버리지 90% 이상을 유지하려 한다.

2. RecPack 라이브러리 — 파이프라인의 각 단계

논문의 그림 1은 전형적인 Top-N 실험 흐름을 보여 준다. 원시 데이터셋을 전처리해 사용자-아이템 상호작용 행렬로 바꾸고, 이를 학습·검증·테스트로 나눈 뒤, 알고리즘을 학습시켜 추천을 만들고, 후처리를 거쳐 지표를 계산한다. RecPack은 각 단계마다 전용 모듈을 둔다.

Datasets. MovieLens, Netflix Prize, YOOCHOOSE(RecSys Challenge 2015), Adressa(뉴스), Retailrocket, CosmeticsShop, CiteULike 등 자주 쓰이는 협업 필터링 데이터셋을 객체 하나로 불러온다(예: MovieLens25M()). 공개 데이터면 자동으로 내려받고, 접근이 제한된 데이터는 경로만 지정하면 된다. 더 중요한 것은 데이터셋마다 기본 전처리 필터가 정의돼 있다는 점이다. 모두가 같은 기본값을 쓰면 서로 다른 논문의 실험을 비교하기 쉬워진다. 물론 기본 필터를 끄고 직접 정할 수도 있고, 내장되지 않은 데이터는 pandas DataFrame으로 불러오면 된다.

Preprocessing. 협업 필터링에서는 원시 로그에 필터를 적용한 뒤 행렬로 변환하는 것이 관례다. RecPack은 7가지 필터를 제공한다.

  • MinUsersPerItem, MinItemsPerUser, MaxItemsPerUser: 너무 드물거나 지나치게 많은 상호작용을 가진 이상치를 제거한다(흔히 말하는 k-core 필터링과 비슷한 역할).
  • NMostPopular, NMostRecent: 아이템 카탈로그 크기를 제한한다.
  • Deduplicate: 같은 사용자-아이템 쌍의 반복 상호작용 중 첫 번째만 남긴다.
  • MinRating: 일정 평점 이상만 남겨 평점 데이터를 implicit feedback으로 바꾼다.

자기 DataFrame에는 DataFramePreprocessor를 만들어 필터를 add_filter로 추가한다. 이 전처리기는 필터 적용과 함께 사용자·아이템 ID를 연속된 행렬 인덱스로 바꿔 준다.

Matrix. 상호작용 데이터는 InteractionMatrix 객체로 표현되며 타임스탬프를 선택적으로 담는다. 같은 데이터를 여러 "뷰"로 꺼낼 수 있다. 상호작용 횟수가 담긴 SciPy csr_matrix, 이를 0/1로 이진화한 행렬, 사용자별로 시간순 정렬된 아이템 시퀀스 등이다. 배경 지식으로 정리하면, 사용자 \(m\)명·아이템 \(n\)개일 때 이진 행렬은

\[ X \in \{0,1\}^{m\times n},\quad X_{ui}=1 \iff \text{사용자 } u \text{가 아이템 } i \text{와 상호작용함} \]

이다. 여기서 \(X_{ui}=0\)은 "싫어함"이 아니라 "관측되지 않음"이라는 점이 implicit feedback의 본질이다. 저자들은 대부분의 실험에서 사용자가 이 객체의 내부를 신경 쓸 필요가 없다고 말한다. 시나리오·알고리즘·파이프라인이 알아서 적절한 뷰를 꺼내 쓰기 때문이다. 순차 모델은 시퀀스 뷰를, 행렬 기반 모델은 희소 행렬 뷰를 쓰는 식이다.

Scenarios. 논문에서 가장 방법론적으로 중요한 모듈이다. 데이터 누수 없이, 그러면서도 실제 사용 상황을 대표하는 과제로 평가하는 것은 어렵다. 어떤 서비스에서는 처음 보는 사용자에게 괜찮은 추천을 하는 것이 중요하고, 다른 서비스에서는 사용자의 바로 다음 행동을 맞히는 것이 중요하다. RecPack은 문헌에 나오는 거의 모든 분할 방식을 시나리오로 제공한다고 밝힌다. 생성자에 validation=False를 주면 학습/테스트 두 부분으로, validation=True를 주면 학습/검증/테스트 세 부분으로 나눈다.

논문 본문에 이름이 나오는 시나리오는 데모에 쓰인 WeakGeneralization뿐이고, 나머지는 문서로 미룬다. 참고로(논문 밖, 공식 문서 기준) 일반적인 구분은 다음과 같다. Weak generalization은 같은 사용자들의 상호작용 일부를 숨겨 맞히게 하므로 테스트 사용자도 학습에 등장한다. Strong generalization은 사용자 자체를 나눠 학습에 없던 사용자의 이력 일부로 나머지를 예측한다. 시간 기반 분할은 특정 시점 이전으로 학습하고 이후를 예측해 "미래 정보 누수"를 막는다. 마지막 아이템 예측은 순차 추천에서 흔히 쓰는 leave-one-out이다.

Algorithms. 20개가 넘는 알고리즘을 다섯 계열로 제공한다. 아이템 간 유사도(Item-KNN, SLIM, Prod2Vec 등), 행렬 분해(WMF, BPRMF 등), 오토인코더(Mult-VAE, RecVAE, EASE), 세션 기반(GRU4Rec, STAN), 시간 인지 알고리즘이다. 모두 scikit-learn의 BaseEstimator 규약을 따른다. 하이퍼파라미터는 생성할 때 넘기고, fit으로 학습하며, predict로 점수를 낸다.

개발을 빠르게 해 주는 세 개의 추상 기반 클래스가 핵심이다. 배경 지식으로 각 클래스가 전제하는 점수 형태를 정리하면 다음과 같다(수식은 일반적인 정식화이며 논문에 적힌 것은 아니다).

  • ItemSimilarityMatrixAlgorithm: 아이템-아이템 유사도 행렬 \(S\in\mathbb R^{n\times n}\)만 학습하면, 점수는 \(\hat X = X S\)로 계산된다. 즉 \(\hat x_{ui}=\sum_j X_{uj}S_{ji}\)로, 사용자가 본 아이템 \(j\)들이 후보 \(i\)와 얼마나 비슷한지를 합산한다. Item-KNN은 \(S\)를 코사인 유사도로, SLIM과 EASE는 \(X\approx XS\)가 되도록 회귀로 \(S\)를 구한다.
  • FactorizationAlgorithm: 사용자 임베딩 \(U\in\mathbb R^{m\times d}\)와 아이템 임베딩 \(V\in\mathbb R^{n\times d}\)를 학습하고 \(\hat X = UV^\top\), 즉 \(\hat x_{ui}=\mathbf u_u^\top\mathbf v_i\)로 점수를 낸다. \(d\)는 잠재 차원이다.
  • TorchMLAlgorithm: PyTorch 모델의 학습 루프처럼 반복되는 공통 로직을 맡아(구체적 기능 목록은 문서 참조), 연구자는 모델 구조와 손실만 작성하면 된다.

이 구조 덕분에 새 알고리즘을 만들 때 "학습된 \(S\)나 \(U,V\)를 어떻게 얻는가"만 구현하면 추천 생성·평가 연결은 기반 클래스가 처리한다.

Postprocessing. 실제 추천 시스템은 모델 예측 뒤에 비즈니스 규칙을 붙인다. 이커머스라면 민감하거나 연령 제한이 있는 상품을 빼고, 뉴스라면 최근 이틀 안에 발행된 기사로 제한하는 식이다. RecPack은 아이템 부분집합만 남기는 SelectItems와 원치 않는 아이템을 빼는 ExcludeItems 두 가지 PostFilter를 제공한다. 오프라인 실험에서도 이 규칙을 적용해야 실제 서비스 조건과 비슷한 평가가 된다는 것이 산업계 저자다운 관점이다.

Metrics. Top-N 랭킹에서 흔히 쓰는 지표들을 제공한다. 사용법 예로 NDCG@20이 나온다. NDCGK(20)을 만들고 정답과 예측을 calculate에 넘기면, value로 사용자 평균값을, results로 사용자별 값을 얻는다. 사용자별 결과를 주는 것은 평균 뒤에 숨은 분포(어떤 사용자 집단에서 모델이 실패하는지)를 분석할 수 있게 해 준다. 배경 지식으로 NDCG@K의 일반적인 정의는

\[ \mathrm{DCG@K}(u)=\sum_{r=1}^{K}\frac{\mathrm{rel}_u(r)}{\log_2(r+1)},\qquad \mathrm{NDCG@K}(u)=\frac{\mathrm{DCG@K}(u)}{\mathrm{IDCG@K}(u)} \]

이다. \(\mathrm{rel}_u(r)\)은 사용자 \(u\)의 추천 목록 \(r\)번째 아이템이 테스트 정답이면 1, 아니면 0이다. 분모 \(\log_2(r+1)\)은 아래 순위일수록 기여를 줄이는 할인이고, IDCG는 정답을 모두 맨 위에 놓았을 때의 최댓값이어서 NDCG는 0~1 사이가 된다. value는 이를 사용자에 대해 평균한 값이다.

Pipelines. 하이퍼파라미터 탐색, 후처리, 여러 지표 평가를 한 번에 묶는다. PipelineBuilder를 만들고, set_data_from_scenario로 시나리오의 학습/검증/테스트 데이터를 넘기고, add_algorithm으로 평가할 알고리즘을, add_metric으로 지표를 추가한 뒤 build()로 파이프라인을 만들어 run()한다. 하이퍼파라미터는 검증 세트에서 최적화 지표 기준으로 고르고, 테스트 세트는 최종 평가에만 쓰는 구조가 "누수 최소화" 주장의 근거다.

3. 설치와 공개

PyPI에서 설치할 수 있고, 문서에는 시작 가이드와 모듈별 상세 설명이 있다. 소스는 GitLab에 공개돼 있으며 라이선스는 AGPL이다. 이슈 제기와 기여는 GitLab의 가이드를 따른다. AGPL은 네트워크로 서비스하는 경우에도 소스 공개 의무가 생길 수 있는 강한 카피레프트라서, 연구용으로는 문제없지만 사내 서비스 코드에 넣을 때는 검토가 필요하다(이 부분은 해설자의 보충).

4. 데모 시나리오

데모는 두 부분이다. 먼저 He 등의 Neural Collaborative Filtering 논문에 나온 MLP 모델을 TorchMLAlgorithm을 상속해 구현하면서 기반 클래스가 개발을 얼마나 줄여 주는지 보여 준다. 그다음 실험을 수행한다. MovieLens25M을 불러 InteractionMatrix로 바꾸고, WeakGeneralization 시나리오로 학습·검증·테스트를 나눈다. 파이프라인에 MLP와 내장 기준선 WMF, BPRMF를 추가하고, 파라미터 그리드, 최적화 지표, 평가 지표를 정의한 뒤 실행해 성능을 비교한다. 결과 수치는 논문에 실려 있지 않다.

흐름을 코드로 옮기면 대략 다음과 같다. 논문 서술을 바탕으로 한 개략 스케치이며, 정확한 인자와 메서드 시그니처는 공식 문서를 확인해야 한다.

from recpack.datasets import MovieLens25M
from recpack.scenarios import WeakGeneralization
from recpack.pipelines import PipelineBuilder

im = MovieLens25M().load()               # 기본 전처리 + InteractionMatrix
scenario = WeakGeneralization(validation=True)  # 분할 비율 등은 문서 참조
scenario.split(im)

pb = PipelineBuilder()
pb.set_data_from_scenario(scenario)
pb.add_algorithm("BPRMF", grid={...})    # 튜닝할 그리드
pb.add_algorithm("WMF", grid={...})
pb.add_metric("NDCGK", 20)
# 최적화 지표 지정(메서드 이름은 문서 참조)
pipeline = pb.build()
pipeline.run()

5. 향후 과제

RecPack은 활발히 유지·개발 중이며, 가까운 시일 안에 beyond-accuracy 지표(Ge 등이 말한 커버리지·세렌디피티 류)와 하이브리드·콘텐츠 기반 알고리즘을 추가할 계획이라고 밝힌다. 이후 저자들은 추천 알고리즘의 구현 정확성을 테스트하는 프레임워크(RecPack Tests, TORS 2023)로 연구를 이어 갔다.

정리 — 엔지니어 관점에서 읽을 포인트

이 논문은 새 모델이 아니라 실험 위생에 관한 기여다. 시나리오를 이름 붙은 객체로 만든 것은 "어떻게 나눴는가"를 코드 한 줄로 명시하게 하고, 기본 전처리와 원 논문 기준 하이퍼파라미터 초기값은 "기준선을 대충 튜닝해서 이긴" 비교를 줄인다. #9 논문이 지적한 신경망 추천의 재현성 위기, 즉 잘 튜닝된 단순 기준선이 많은 최신 모델을 이긴다는 문제의식에 대한 도구 차원의 응답으로 볼 수 있다.

용어·배경 정리

Implicit feedback
클릭·조회·구매처럼 사용자가 명시적으로 평가하지 않은 행동 로그. 관측된 것은 양성으로 볼 수 있지만, 관측되지 않은 것은 부정인지 미노출인지 알 수 없다.
Top-N 추천
점수(평점)를 정확히 맞히는 대신 사용자에게 보여 줄 상위 N개 목록의 품질을 평가하는 과제. NDCG@K, Recall@K 같은 랭킹 지표를 쓴다.
재현성(reproducibility)과 재사용성(reusability)
재현성은 같은 코드·데이터로 같은 결과가 나오는 것, 재사용성은 그 코드를 다른 데이터·맥락에 쉽게 적용할 수 있는 것이다. 논문은 후자가 과학의 진전 속도를 높인다고 강조한다.
데이터 누수(data leakage)
평가 시점에 알 수 없어야 할 정보가 학습이나 튜닝에 섞이는 것. 테스트 세트로 하이퍼파라미터를 고르거나, 무작위 분할로 미래 상호작용을 학습에 쓰는 것이 대표적이다.
Weak / Strong generalization
Weak는 학습에 등장한 사용자의 숨겨진 상호작용을 예측하고, Strong은 학습에 없던 사용자의 일부 이력으로 나머지를 예측한다. Mult-VAE 논문 등에서 쓰인 구분이다.
scikit-learn 추정기 규약
하이퍼파라미터는 생성자에서 받고, fit으로 학습, predict로 예측하는 통일된 인터페이스. 그리드 탐색 같은 도구와 조합하기 쉬워진다.
아이템 유사도 모델 (Item-KNN, SLIM, EASE)
점수를 \(\hat X = XS\)로 계산하는 계열. \(S\)를 유사도 공식으로 정하면 Item-KNN, 회귀로 학습하면 SLIM·EASE가 된다. 단순하지만 강한 기준선으로 자주 쓰인다.
WMF / BPRMF
WMF는 관측 여부에 신뢰도 가중치를 둔 제곱 오차로 행렬을 분해하고(Hu·Koren·Volinsky), BPRMF는 "본 아이템 점수 > 안 본 아이템 점수"라는 쌍 비교 손실로 분해한다(Rendle 등).
AGPL
GNU Affero GPL. 수정한 소프트웨어를 네트워크 서비스로 제공하는 경우에도 소스 공개 의무가 생길 수 있는 카피레프트 라이선스.

이해도 점검 질문

  1. [사실] RecPack이 기존 툴킷(Elliot, RecBole, DaisyRec 등)과 스스로를 구분하는 핵심 지점은? (a) 더 빠른 GPU 학습 (b) 설정 파일·CLI 중심 벤치마킹이 아니라 노트북에서의 반복적 알고리즘 개발 지원 (c) 평점 예측 과제 지원 (d) 온라인 A/B 테스트 기능
    정답 보기(b). 기존 툴킷은 최신 알고리즘들의 빠르고 정확한 비교(벤치마킹)에 초점을 두고 설정 언어나 명령줄로 접근하게 하지만, RecPack은 연구자가 자기 알고리즘을 반복적으로 다듬고 디버깅하는 과정을 돕는 것을 목표로 한다.
  2. [사실] RecPack이 제공하는 세 가지 추상 기반 클래스의 이름을 쓰라.
    정답 보기ItemSimilarityMatrixAlgorithm, FactorizationAlgorithm, TorchMLAlgorithm. 각각 아이템 유사도, 행렬 분해, PyTorch 기반 모델 계열의 공통 로직을 담는다.
  3. [사실] 데모에서 사용한 데이터셋, 시나리오, 비교 대상 알고리즘은?
    정답 보기MovieLens25M 데이터셋, WeakGeneralization 시나리오. 직접 구현한 MLP(He 등의 NCF 논문)를 내장 기준선 WMF, BPRMF와 비교했다. 논문에 결과 수치는 실리지 않았다.
  4. [원리] 데이터셋마다 "기본 전처리 필터"를 정의해 두는 것이 연구 커뮤니티에 어떤 이점을 주는가?
    정답 보기같은 데이터셋이라도 최소 상호작용 수, 중복 처리, 평점 임계값 등에 따라 결과가 크게 달라진다. 모두가 같은 기본값을 쓰면 서로 다른 논문의 실험이 비교 가능해지고, 전처리 차이로 생기는 착시를 줄인다.
  5. [원리] 시나리오 생성자에 validation=True를 주는 것이 "누수 최소화"와 어떻게 연결되는가?
    정답 보기학습/검증/테스트 세 부분으로 나누어 하이퍼파라미터는 검증 세트로만 고르고 테스트 세트는 최종 평가에만 쓰게 된다. 테스트 세트로 튜닝하면 보고 성능이 과대평가되는데, 파이프라인이 이를 구조적으로 막아 준다.
  6. [원리] ItemSimilarityMatrixAlgorithm을 상속해 새 알고리즘을 만든다면, 연구자가 구현해야 하는 핵심은 무엇이고 점수는 어떻게 계산되는가?
    정답 보기아이템-아이템 행렬 \(S\)를 학습하는 부분(fit)만 구현하면 된다. 점수는 \(\hat X = XS\), 즉 사용자가 상호작용한 아이템들과 후보 아이템의 유사도를 합산해 계산되며, 이 예측·평가 연결은 기반 클래스가 처리한다(일반 정식화 기준).
  7. [해석] 지표 객체가 사용자 평균값(value)과 사용자별 값(results)을 둘 다 제공하는 것이 왜 유용한가?
    정답 보기평균이 같아도 분포는 다를 수 있다. 사용자별 값이 있으면 이력이 짧은 사용자, 헤비 유저 등 집단별 성능을 나눠 보거나, 두 모델 간 사용자 단위 쌍 비교로 통계적 유의성을 검정할 수 있다.
  8. [해석] 오프라인 실험에 ExcludeItems 같은 후처리를 넣는 것이 평가 결과 해석에 어떤 영향을 주는가?
    정답 보기실제 서비스에서는 비즈니스 규칙 때문에 일부 아이템이 노출될 수 없다. 이를 무시하면 서비스에서 보여 줄 수 없는 아이템을 맞혀서 점수를 얻는 모델이 과대평가된다. 후처리를 넣으면 오프라인 지표가 실제 서빙 조건에 더 가까워진다.
  9. [비판] 이 논문의 주장을 검증하기에 부족한 점은 무엇이며, 어떤 실험이나 증거가 있으면 좋겠는가?
    정답 보기데모 논문이라 정량 근거가 없다. 예를 들어 같은 설정에서 다른 툴킷과 같은 수치가 재현되는지, 학습·평가 속도, 기반 클래스 사용 시 코드량 감소, 사용자 연구(개발 시간 단축) 등이 있으면 "재현 가능하고 재사용 가능한 실험을 돕는다"는 주장이 더 탄탄해진다. 예시 답안이다.
  10. [적용] 사내 추천팀이 새 후보 생성 모델을 오프라인 검증할 때 RecPack의 설계 원칙 중 무엇을 차용하겠는가? 그대로 쓰기 어려운 점은?
    정답 보기차용할 점: 분할 방식을 이름 붙은 시나리오로 고정(특히 시간 기반 분할), 검증/테스트 분리 튜닝, 기준선(EASE·Item-KNN 등) 하이퍼파라미터의 공정한 튜닝, 비즈니스 규칙을 반영한 후처리, 사용자별 지표 저장. 어려운 점: 수억 규모 상호작용은 단일 머신 희소 행렬로 다루기 어렵고, 피처가 풍부한 랭킹 모델은 범위 밖이며, AGPL 라이선스로 서비스 코드 통합은 법무 검토가 필요하다. 예시 답안이다.
